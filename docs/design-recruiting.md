# 企业招聘工作区设计

## 服务对象

企业招聘负责人和技术岗位负责人。该角色负责维护可发布、可解释、带时间范围的岗位能力版本。

## 首要任务

```text
发现岗位变化 -> 查看证据 -> 审核变化 -> 发布岗位版本 -> 诊断候选人
```

页面不要求用户先理解日报、预测、模型或数据库。所有内部计算都必须汇聚为岗位版本决策。

## 入口与导航

首次进入时提供任务选择：

```text
[更新既有岗位] [定义新岗位] [诊断候选人]
```

企业招聘工作区导航：

```text
工作台 / 我的岗位 / 新岗位候选 / 候选人诊断 / 能力图谱
```

审核、评测和质量看板属于内部审核工作区，不与业务导航并列。

## 工作台首屏

首屏只回答三个问题：哪个岗位需要决定、当前处于什么阶段、下一步是什么。

```text
AI 应用工程师
当前版本 v1.5 · 13 项变化待审核
当前阶段：审核能力变化
下一步：查看证据并完成审核
```

工作台区域：

1. 优先事项：一个主岗位和一个主行动按钮。
2. 我的岗位：当前生效版本、最近变化和状态。
3. 快捷操作：更新既有岗位、定义新岗位、诊断候选人。
4. 最近活动：版本发布、审核完成和诊断结果。

不得在首屏突出 run_id、模型版本、评测集或原始事件流。

## 岗位发现

首屏回答：市场出现了什么新岗位、它凭什么不是既有岗位。

```text
左：候选列表（名称 / 增长 / 覆盖公司数 / 来源数 / 置信度 / 审核状态）
右：选中候选
  与最相似既有岗位对比：共享技能、独有技能、职责边界
  定义卡：名称 / 核心职责 / 必备技能 / 加分技能 / 典型行业场景
  证据摘要：JD 样本、跨公司覆盖、信号引用
```

规则：

- 候选列表只显示增长、覆盖、置信度和审核状态，不先展示模型过程。
- “为什么不是既有岗位”用与最相似岗位的可见对比回答，不用模型口头解释。
- 定义卡五要素均可编辑；编辑后进入审核，审核记录与版本关联。
- 每项技能和职责可打开证据抽屉（来源、原文片段、时间）。
- 发布成功后提供“查看能力图谱”与“发起候选人诊断”两个后续动作。

状态：

```text
候选 -> 草稿 -> 审核中 -> 已发布 / 已拒绝
```

## 岗位更新流程

页面不增加全局流程横条。岗位、版本和时间窗由左侧上下文区承载，审核状态与发布动作在对应内容标题栏就地呈现。

主页面布局：

```text
左：岗位、基准版本、基准窗/观察窗和样本摘要
中：新增/删除/修改三列，列内独立滚动
右：分析记录、审核队列和完成状态
```

每项变化按以下顺序展示：

```text
能力名称 -> 变化类型 -> 相对变化 -> 证据数量 -> 审核动作
```

版本、时间窗和样本数只在左侧上下文区出现一次。右侧审核队列只保留总待处理数和任务明细，不重复中央列统计。

发布按钮固定在中间面板标题栏右侧：

- 有未审核项：禁用，悬浮说明阻塞原因；
- 全部审核完成：可发布；
- 发布成功：显示版本号及可用下游动作。

## 能力图谱

首屏回答：这个岗位需要什么能力、它和相邻岗位的边界是什么。

```text
顶：技术栈（AI / 大数据 / 智能系统 / 物联网）与职级（初 / 中 / 高）筛选
中：图谱（岗位 -> 能力域 -> 技能点），技能点为最小可操作粒度
右：节点详情侧栏（信息 / 别名 / 兄弟技能点 / 证据摘要 / 关联岗位版本与市场信号）
```

规则：

- 节点颜色规则沿用 `design.md`：必备蓝、加分中性、新增黄、删除红、待审核虚线。
- 图谱只投影已发布岗位版本；草稿与预测建议不进入图谱。
- 节点详情固定包含版本、时间和证据；市场信号（JD 提及数与占比）作为次级区块。
- 从岗位节点可直接进入候选人诊断，携带当前 `job_version_id`。
- Neo4j 不可用时降级为版本列表视图，图谱区域提示暂不可用。

## 候选人诊断

首屏回答：这位候选人的关键短板是什么、按哪版岗位评估。

页面不增加全局流程横条。岗位版本在匹配报告标题区呈现，简历导入、画像修正和重新计算分别放在对应内容区域。

```text
左：候选人画像（技能、熟练度、年限、项目证据，可修正）
中：匹配报告（已具备 / 部分具备 / 缺失，关键短板置顶）
右：岗位依据与证据（按已发布版本的能力要求展开）
底：学习路径（按必备性、权重、前置依赖排序）
```

规则：

- 简历上传与解析确认是流程内的第一步，不是独立页面；解析失败保留原文件并转手工录入。
- 无法标准化的技能显示“待确认”，不计入已具备。
- 用户修正画像后一键“重新计算”；每次修正记入 `user_corrections` 审计。
- 首屏先显示关键必备技能是否缺失；总匹配分只作辅助，不遮蔽短板。
- 招聘侧可在运行详情内查看置信度与算法版本；不输出录用或淘汰结论。
- 岗位版本过期时提示切换到最新已发布版本，并保留历史对照。

## 证据与状态

结论、变化、依据、行动必须在一次展开内完成。证据抽屉展示来源、发布时间、原文片段、反证和审核记录。

业务状态优先使用：

```text
待审核 / 证据不足 / 审核中 / 已确认 / 可发布 / 已发布 / 已过期
```

技术字段放入“运行详情”中，不作为主标题。

## 发布后的承接

发布成功页必须明确：

```text
岗位版本已发布
现在可以：查看能力图谱 / 诊断候选人 / 生成培养任务
```

岗位版本是图谱、匹配和培养输出的唯一标准锚点；预测建议不能直接进入发布结果。

## 权限边界

企业招聘负责人可以查看和编辑岗位草稿、审核变化、发布版本、发起候选人诊断；不能查看个人之外的敏感简历，也不直接修改历史已发布版本。

## 验收标准

- 首屏能看到一个明确的岗位决策和下一步行动；
- 用户无需理解预测或数据管线即可完成岗位更新；
- 每项发布变化可回到证据和审核动作；
- 发布后能直接进入图谱、诊断或培养输出；
- 同一业务数字只保留一个主要视觉表达。

## 数据接入原则

企业招聘工作区的正常路径必须使用 API 展示模型 和已发布岗位事实。`data/fixtures/` 只用于显式的空态、错误态、离线测试和前端单元测试，不作为正常首屏数据。

页面标签应反映真实来源：

```text
已发布版本 / 真实处理产物 / 评测快照 / 离线回测 / 合成候选人
```

内部 `run_id`、模型版本和数据集版本可以通过运行详情查看，但不能因为前端使用 fixture 就把整个业务页面标记为演示数据。
